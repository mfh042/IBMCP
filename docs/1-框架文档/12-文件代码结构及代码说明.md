### 2.3 `core/collector/` 采集扩展适配层（三个文件的关系）

- [protocol.py](file:///E:/999-Dev/01-IBMCP-黑盒管控系统/02-IBMCP/backend/app/core/collector/protocol.py)：**契约定义**。`CollectorError` 基类 + 6 个带 `rc` 码的子类（ProtocolNotSupported=1 … DeviceNotInPlan=6）；`RC_TO_CODE` / `CLASS_TO_RC` 把 rc 映射成 HTTP 业务码；`to_api_error()` 统一翻译；`CollectorApi` 是 `typing.Protocol`，声明扩展必须实现的 9 个方法签名。
- [ffi.py](file:///E:/999-Dev/01-IBMCP-黑盒管控系统/02-IBMCP/backend/app/core/collector/ffi.py)：**生产实现**。`NativeCollector` 懒加载 `industrial_collector._core`（pybind11 编译的 `.so`），把每个方法的异常转成 `CollectorError` 并保留 `rc/stage/device_key/point_id`；`get_collector(backend)` 工厂按 `COLLECTOR_BACKEND` 返回 `stub` 或 `native` 单例。
- [stub.py](file:///E:/999-Dev/01-IBMCP-黑盒管控系统/02-IBMCP/backend/app/core/collector/stub.py)：**Windows 开发桩**。`StubCollector` 严格复刻真实扩展的校验语义与错误码（不做真实 IO），`snapshot_since` 产出模拟递增采样、`write_point` 同步回推 `write_result` 事件，让 Windows 侧能跑通与欧拉一致的全链路错误分支。

> 关系：`protocol.py` 定接口 → `stub.py` / `ffi.py` 是两种实现 → `deps.get_collector_backend()` 按配置选一个注入所有路由。

## 3. 主流程走读

### 3.1 用户在前端激活配置 → 数据进库并 WS 推送

1. 前端调用 `POST /api/v1/config/equipments/{id}/activate` → [running_config.py#activate_config](file:///E:/999-Dev/01-IBMCP-黑盒管控系统/02-IBMCP/backend/app/api/v1/running_config.py#L222)。
2. → `CollectorOrchestrator.activate_config()` [collector_orchestrator.py#L43](file:///E:/999-Dev/01-IBMCP-黑盒管控系统/02-IBMCP/backend/app/services/collector_orchestrator.py#L43)：置 `running_equipment_config.config_status=1` → 取 `MAX(revision)+1` → `PlanCompiler.compile_full()` 全量编译。
3. → `PlanCompiler` 用 `_COMPILE_SQL` 一次查五级链 → `_build_plan()` 生成 `{devices, plan_hash}` [plan_compiler.py#L121](file:///E:/999-Dev/01-IBMCP-黑盒管控系统/02-IBMCP/backend/app/services/plan_compiler.py#L121)。
4. hash 变化 → `_apply()` [collector_orchestrator.py#L149](file:///E:/999-Dev/01-IBMCP-黑盒管控系统/02-IBMCP/backend/app/services/collector_orchestrator.py#L149)：`collector.apply_plan(plan, revision)` → 扩展回推 `plan_ack` / `device_status` 事件 → `_sync_runtime_snapshot()` 把计划投影到 `using_devices`/`using_points` → 插 `runtime_plan_revision`。
5. 扩展采集线程持续产出采样 → 回调 `EventDispatcher._on_event`（仅入队）[event_dispatcher.py#L53](file:///E:/999-Dev/01-IBMCP-黑盒管控系统/02-IBMCP/backend/app/services/event_dispatcher.py#L53)；`device_status` 事件更新设备在线状态并 WS `device` 广播。
6. `SamplePump._tick()` 每 200ms 拉 `snapshot_since` [ingest_service.py#L139](file:///E:/999-Dev/01-IBMCP-黑盒管控系统/02-IBMCP/backend/app/services/ingest_service.py#L139) → `_batch_copy_ts()` 用 `COPY` 写 `time_series_data` → `_evaluate_alarms()` 判定报警写 `using_alarms` → `ws_hub.broadcast("data", ...)` 和 `broadcast("alarm", ...)`。
7. 前端 WS 客户端（[ws/IbmcpWsClient.ts](file:///E:/999-Dev/01-IBMCP-黑盒管控系统/02-IBMCP/frontend/src/ws/IbmcpWsClient.ts) / [stores/ws.ts](file:///E:/999-Dev/01-IBMCP-黑盒管控系统/02-IBMCP/frontend/src/stores/ws.ts)）订阅 `data` 主题，实时刷新看板。

### 3.2 控制命令 `write` → `wait=true` 回执

1. 前端 `POST /api/v1/control/write` 带 `{device_code, point_id, value, wait:true, timeout}` → [control.py#write_point](file:///E:/999-Dev/01-IBMCP-黑盒管控系统/02-IBMCP/backend/app/api/v1/control.py#L15)。
2. → `ControlService.write()` [control_service.py#L30](file:///E:/999-Dev/01-IBMCP-黑盒管控系统/02-IBMCP/backend/app/services/control_service.py#L30)：校验点位/读写权限/在线/控制功能绑定/值类型。
3. `key=command_key(device_code, point_id)` → `fut = command_waiter.register(key)`（**先注册**，因为扩展可能在 `write_point` 内同步回调）[control_service.py#L103](file:///E:/999-Dev/01-IBMCP-黑盒管控系统/02-IBMCP/backend/app/services/control_service.py#L103)。
4. `cmd_id = collector.write_point(...)` → 写 `control_commands`（status=0，存 `ext_command_id=cmd_id`）。
5. 扩展回推 `write_result` 事件 → `EventDispatcher._on_write_result()` [event_dispatcher.py#L135](file:///E:/999-Dev/01-IBMCP-黑盒管控系统/02-IBMCP/backend/app/services/event_dispatcher.py#L135)：更新 `control_commands` status（2 成功/3 失败）→ WS `control` 广播 → `command_waiter.resolve(key, payload)`。
6. `write()` `await asyncio.wait_for(fut, timeout)` 拿到回执返回；超时抛 4102。

## 9. 已知未落地 / 与文档不一致之处

如实列出，便于新开发者避坑：

1. **表数量 28 ≠ 旧述 29**：三个迁移文件实际 `CREATE TABLE` 28 次（0001:26 / 0002:2 / 0003:0，0003 只给 `control_commands` 加列）。部分旧文档写「29 张」不准确，以代码为准。
