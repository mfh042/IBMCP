## 一、方案定位与目标

### 1.1 前端职责

IBMCP 前端是后端业务域的 **1:1 投影**，承担四大职责：

1. **配置向导**：把后端五级配置链（装备实例 → 工艺路线绑定 → 设备绑定 → 采集项配置 + 装备功能启用）呈现为向导式页面
2. **实时监控**：订阅后端 WebSocket 四类推送主题（`data` / `device` / `alarm` / `control`），实现数据看板秒级刷新
3. **运维管理**：设备树、点位配置、历史趋势查询、控制命令下发、报警确认闭环
4. **系统管理**：用户/角色 CRUD、RBAC 权限分配、JWT 登录态维护

### 1.2 一套代码，三种运行形态

> 用户要求：前端在 nginx 中运行、可以 android-app 模式运行、可执行文件运行、web 网页访问、可部署到 Windows / Linux。

| 形态            | 目标平台                                     | 技术壳                                          | 部署方式                        | 产物                                      |
|-----------------|----------------------------------------------|-------------------------------------------------|---------------------------------|-------------------------------------------|
| **Web 浏览器**  | 任意（Chrome 90+ / Edge / Firefox / Safari） | 纯 SPA，无壳                                    | Vite build → Nginx 托管静态资源 | `dist/` 静态文件                          |
| **桌面应用**    | Windows 10+ / openEuler(Debian 系)           | **Tauri 2.x**（系统 WebView + Rust 后端壳）     | `tauri build` 生成安装包        | `.msi`(Win) / `.deb` / `.AppImage`(Linux) |
| **Android App** | Android 8.0+                                 | **Tauri 2.x Android**（系统 WebView + Rust 壳） | `tauri android build` 生成 APK  | `.apk` / `.aab`                           |

**为什么选 Tauri 2.x 而不是 Electron + Capacitor 双套**：

- Tauri 2.x 同时支持桌面（Windows / Linux / macOS）和移动端（Android / iOS），**一套代码覆盖三种形态**，无需维护两套壳工程
- 使用操作系统自带 WebView2（Windows）/ WebKitGTK（Linux）/ Android System WebView，安装包 5-15MB、内存 30-80MB，更适合工业现场工控机长期运行
- Electron 内嵌完整 Chromium，单应用 150MB+、内存 200MB+，不适合工业现场

### 1.3 多端差异屏蔽原则

前端代码分为两层：

```
┌─────────────────────────────────────────────┐
│  业务层（src/）：Vue 组件 / Store / API / WS  │  ← 三种形态 100% 共用
│  不感知运行环境，不写 if (isTauri) / isAndroid  │
├─────────────────────────────────────────────┤
│  适配层（src/comm/）：HTTP / WS / 环境检测    │  ← 启动时根据运行形态注入不同实现
└─────────────────────────────────────────────┘
```

- **业务层零环境判断**：所有页面、组件、Store 不直接写 `window.__TAURI__` 或判断 `isAndroid`
- **适配层统一注入**：`src/comm/env.ts` 提供 `EnvDetector`（`isTauri`/`isDev`/`runtimeLabel`），`src/comm/config.ts` 提供
  `CommConfig`（`apiBase`/`wsUrl` getter，按 env → localStorage 用户覆盖 → 默认值的三级回退顺序解析），`src/comm/http.ts` /
  `src/comm/ws.ts` / `src/comm/tauri.ts` 提供具体实现
- **系统能力按需调用**：Tauri 形态特有能力（Rust 命令 `get_api_config`/`set_api_config`/`check_backend_health`）通过
  `src/comm/tauri.ts` 的 `tauriCommands` 对象暴露，Web 形态下静默降级

### 1.4 现状 vs 重构目标差异总表（FastAPI 重构时前端同步改造清单）

FastAPI**。两列对照：

| **路由命名空间**       | 11 个独立前缀：`/api/auth`、`/api/running/configs`、`/api/dicts`、`/api/base-devices`、`/api/equipments`、`/api/devices`、`/api/history`、`/api/alarms`、`/api/config/devices`、`/api/config/points`、`/api/collector` | 8 个规范组：`/api/v1/auth`、`/api/v1/static`、`/api/v1/config`、`/api/v1/runtime`、`/api/v1/data`、`/api/v1/alarms`、`/api/v1/control`、`/api/v1/collector` | P0         |
| **静态字典前缀**       | `GET /api/dicts/categories/all`、`/api/base-devices/items` 分散两套                                                                                                                                                    | 统一工厂 `GET /api/v1/static/{resource}/all`（`device-categories`、`device-data-items` 等）                                                                 | P0         |
| **运行配置前缀**       | `GET /api/running/configs`、`/api/running/configs/{id}/expand`                                                                                                                                                         | `GET /api/v1/config/equipments`、`/api/v1/config/equipments/{id}/expand`                                                                                    | P0         |

| **HTTP 响应解包**      | 接受 `code=0` 或 `code=200` 都算成功；有 `items → list` 结构适配                                                                                                                                                       | 只认 `code=0`（见 03 号 Result 结构定义）                                                                                                                   | P1         |
| **路由表**             | `/monitoring/dashboard`、`/devices/:id`、`/equipment-config/wizard`、有独立 `/routes` `/equipments` 路由                                                                                                               | `/dashboard`、`/devices/:deviceCode`、`/config/equipments/:id/wizard`（收进配置子路径）                                                                     | P1         |
| **目录层命名**         | `src/comm/`（HTTP/WS/环境检测）                                                                                                                                                                                        | 设计稿曾叫 `src/adapters/`，实际 `comm/` 结构更简洁，**保留现状**                                                                                           | 不变       |
| **Collector 探针接口** | `/api/ping`、`/api/collector/status`（raw JSON 特殊处理）                                                                                                                                                              | `/api/v1/collector/protocols`、`/health`、`/api/v1/collector/stats`                                                                                         | P2         |
| **authStore 字段**     | 无 `refreshToken`（JWT 自动解码）                                                                                                                                                                                      | 有 `refreshToken`（后端 03 号 `/auth/refresh` 端点）                                                                                                        | P1         |

> **改造顺序建议**：先用 Vite proxy 把 `/api/v1/*` 映射到后端，让前端能同时对接新老两套 API（通过 `.env` 切换），然后逐个模块迁移。WS
> 协议改造影响面较大，建议放在 HTTP 接口对齐之后。

> 负责平台安全与访问控制，覆盖授权认证、用户管理、角色权限分配。
> 对应后端 `/api/v1/auth/*`。

### 4.2 RBAC 权限模型

```
users ────(多对多)──── user_roles ────(多对多)──── roles
  │                                                  │
  │ 前端路由守卫                                       │ 后端接口鉴权
  │ useAuthStore().userInfo.roles                    │ require_roles 依赖
  │                                                  │
  └────────── roles: ['admin', 'engineer', ...] ────┘
```

**系统预设角色与模块可见性**（前端菜单隐藏只是体验优化，安全边界在后端）：

| role       | 系统管理 | 基础数据 | 运行配置 | 控制监控          |
|------------|----------|----------|----------|-------------------|
| `admin`    | 读写     | 读写     | 读写     | 读写              |
| `engineer` | 只读     | 读写     | 读写     | 读写              |
| `operator` | 不可见   | 只读     | 只读     | 只读 + ack + 控制 |
| `viewer`   | 不可见   | 只读     | 只读     | 只读              |

### 4.3 JWT Store 设计

```typescript
// stores/auth.ts
export const useAuthStore = defineStore('auth', {
  state: () => ({
    token: localStorage.getItem('ibmc_token') || '',
    refreshToken: localStorage.getItem('ibmc_refresh') || '',
    userInfo: JSON.parse(localStorage.getItem('ibmc_user') || 'null') as null | {
      id: number; username: string; displayName: string; roles: string[]
    },
  }),
  getters: {
    isLoggedIn: (s) => !!s.token,
    hasRole: (s) => (role: string) => s.userInfo?.roles.includes(role) ?? false,
  },
  actions: {
    async login(username: string, password: string) {
      const { data } = await authApi.login(username, password)
      this.token = data.token
      this.refreshToken = data.refresh_token
      this.userInfo = { id: data.id, username: data.username, displayName: data.displayName, roles: data.roles }
      localStorage.setItem('ibmc_token', this.token)
      localStorage.setItem('ibmc_refresh', this.refreshToken)
      localStorage.setItem('ibmc_user', JSON.stringify(this.userInfo))
    },
    logout() {
      this.token = ''
      this.refreshToken = ''
      this.userInfo = null
      localStorage.removeItem('ibmc_token')
      localStorage.removeItem('ibmc_refresh')
      localStorage.removeItem('ibmc_user')
      router.push('/login')
    },
  },
})
```

## 五、模块二：基础数据管理

> 负责 10 张 `base_` 前缀静态表的 CRUD，对应后端 `/api/v1/static/*`。
> 所有静态字典走统一的"六件套"模式：`list` / `all` / `detail` / `create` / `update` / `remove`。

### 5.1 功能点清单

| 功能点     | 页面                    | 接口                          | 关键变化                                     |
|------------|-------------------------|-------------------------------|----------------------------------------------|
| 设备分类   | `DeviceCategoryView`    | `/static/device-categories`   | 走工厂六件套                                 |
| 品牌型号   | `DeviceBrandView`       | `/static/device-brands`       | 唯一键改组合                                 |
| 端口字典   | `DevicePortView`        | `/static/device-ports`        | —                                            |
| 协议字典   | `DeviceProtocolView`    | `/static/device-protocols`    | 新增 `has_driver` 字段，无驱动项置灰         |
| 数据项字典 | `DataItemView`          | `/static/device-data-items`   | 新增 scale/offset/alarm 5 字段，表单必须补齐 |
| 基础设备   | `DeviceBaseView`        | `/static/devices`             | `supported_protocols` 用扩展清单校验         |
| 装备主数据 | `EquipmentView`         | `/static/equipments`          | —                                            |
| 装备功能   | `EquipmentFunctionView` | `/static/equipment-functions` | —                                            |
| 工艺路线   | `ProcessRouteView`      | `/static/process-routes`      | 级联工步（保持）                             |
| 工步       | 路线详情内              | `/static/process-steps`       | 复合键路径                                   |

### 5.2 前端必须同步改的 3 处（否则配置完采不到）

1. **数据项字典表单**：新增 `scale` / `offset` / `alarm_high` / `alarm_low` / `alarm_enabled` 五个输入项；`scale` 加前端校验
   `!= 0`（该值为 0 会让读数恒定）。
2. **协议下拉**：数据源从 `GET /static/device-protocols/all` 改为 `GET /api/v1/collector/protocols`（或
   `/static/device-protocols/all?with_driver=true`），**只允许选扩展真支持的**。
3. **地址字段**：数据项表单把 `address_rule` 从"可选"改为**必填**（纯控制项除外），标签明确写"通信地址（非编码）"。

### 5.3 字典缓存策略

```typescript
// stores/dictionaries.ts
const KEY = 'ibmcp_dict_v1'
state: { version: 1, cache: Record<string, any[]>, loadedAt: {} }
```

内存 + localStorage + 版本号三级缓存，配合后端 `/all` 的 Redis 缓存，前端页面切换时字典加载从"数百毫秒 DB
扫描"降到"毫秒级读取"。

### 7.2 DashboardView 数据流

```
1. GET /runtime/devices/{device_key}/points    → 点位静态信息（名称/单位/量程/质量码枚举）
2. WS subscribe('data')                        → 全局数据流，前端按 point_id 命中
3. 实时值渲染 RealTimePoint                     → wsStore.realtimeData[point_id]
4. 折线图滑动窗口 100 点                         → 保持
```

> **不要试图改成"按点位订阅"**：`topic` 是固定字符串、不能带 `:id`。保持全局 `data` 主题，前端过滤。

```
ControlDialog 提交 → POST /api/v1/control/{device_code}/write

  响应：{ command_id, accepted, message }
  → 前端把 command_id 记入 pendingCommands
  → WS 订阅 'control' 主题
  → 收到 control_finished 且 command_id 匹配 → 更新状态、提示结果
```

### 9.1 四种运行形态识别（`comm/env.ts`）

// 实际代码的 EnvDetector —— 通过 window.__TAURI__ 标志 + import.meta.env 区分
export function detectEnv() {
  const isTauri = typeof window !== 'undefined' && '__TAURI_INTERNALS__' in window
  const isDev = import.meta.env.DEV
  const isProductionWeb = !isTauri && !isDev
  const isRemoteBrowser = !isTauri && !isProductionWeb // Vite dev proxy
  
  const runtimeLabel = isTauri ? 'Tauri' : isDev ? 'Vite Dev' : 'Production Web'
  return { isTauri, isDev, isProductionWeb, isRemoteBrowser, runtimeLabel }
}

## 十、WebSocket 客户端封装（`ws/IbmcpWsClient.ts`）

> ⚠️ **实际代码与 03 号文档有差异**：端点 `/ws/push`、载荷字段驼峰命名。重构后目标统一为 **`/api/v1/ws/collect`** + 全蛇形。

### 10.1 连接地址

| 运行形态   | WS URL（实际）                                                    | 重构后（对齐 03 号）                                                    |
|------------|-------------------------------------------------------------------|-------------------------------------------------------------------------|
| Vite dev   | `/ws` → proxy `ws://127.0.0.1:8000/ws`（target 由 `VITE_API_TARGET` 推导） | `ws://127.0.0.1:8000/api/v1/ws/collect?token=<jwt>`（命中 `/api` 规则）  |
| 生产 Web   | 推断 `${protocol}//${host}/ws/push?token=<jwt>`                   | Nginx 反代 `location /api/v1/ws/collect`                                |
| Tauri 桌面 | `.env.tauri` 写死 `ws://192.168.80.130:8080/ws/push?token=<jwt>`  | 同 Vite dev 端口，或用户 localStorage 覆盖                              |

> **为什么 dev 期 WS 走 `/api/v1/ws/collect` 也能通**：`vite.config.ts` 的 proxy 只声明了 `/api` 与 `/ws` 两个 key，
> 而 `/api/v1/ws/collect` 命中 `/api` 规则（`changeOrigin: true`，未开 `ws: true`）。**Vite 的 `/api` 规则没有 `ws: true`**，
> 所以严格来说只有 `/ws` 前缀的 WS 升级会被正确代理。**联调时若 WS 握手失败**，两种解法：① 保持后端路径 `/api/v1/ws/collect`，
> 在 `vite.config.ts` 给 `/api` 规则加 `ws: true`；② 在 Nginx/Vite 之间做路径重写。**推荐 ①**，改动最小且不影响生产。

**鉴权**：连接时 URL query 带 `?token=<jwt>`（浏览器 WS API 无法设自定义 Header）。

### 10.2 协议帧（与 03 号文档 5.1 节一致）

```
首帧（客户端）：{"type":"subscribe","topic":"data"}
服务端确认：  {"type":"subscribed","topic":"data"}
保活：        {"type":"ping"} → {"type":"pong"}
退订：        {"type":"unsubscribe","topic":"data"}
```

### 10.3 四主题载荷契约（实际 vs 目标）

| 主题      | 实际载荷（驼峰）                                                                                                                 | 重构后（对齐 03，全蛇形）                                                                   | 前端处理                                        |
|-----------|----------------------------------------------------------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------|-------------------------------------------------|
| `data`    | `{ type:"data", deviceId, pointId, value, quality, ts, error }`                                                                  | `{ type:"data", device_code, point_id, value, quality, ts, error }`                         | 按 `pointId` 命中 → 更新 `wsStore.realTimeData` |
| `device`  | `{ type:"device_status", deviceId, status(0/1/2), ts, reason }`                                                                  | `{ type:"device_status", device_code, status, ts, reason }`                                 | 按 `deviceId` 命中 → 更新设备在线态             |
| `alarm`   | `alarm_triggered` / `alarm_acknowledged` / `alarm_recovered`，载荷嵌套 `alarm:{ alarmId, pointId, triggeredAt, acknowledgedAt }` | 同结构但字段改蛇形 `alarm_id` / `triggered_at` / `acknowledged_at`                          | upsert 到报警列表，更新横幅计数                 |
| `control` | `{ type:"control_finished", commandId, deviceId, pointId, success, status, message, value, finishedAt }`                         | `{ type:"control_finished", command_id, device_code, point_id, success, ..., finished_at }` | 按 `commandId` 命中 → 更新控制结果弹窗          |

> **重构提示**：03 号文档定义的是全蛇形（`device_code` / `point_id` / `triggered_at`），实际代码是驼峰（`deviceId` /
> `pointId` / `triggeredAt`）。**两种方案二选一**，建议统一到 03 号文档的蛇形契约，前端在 `types/api.ts` 的 WS payload
> interface 上一次性改过来。

### 10.4 心跳与重连（实际代码实现）

```
Heartbeat：30s 定时发 {"type":"ping"}
重连策略：指数退避
  attempt 1 → delay 1s
  attempt 2 → delay 2s
  attempt 3 → delay 4s
  ...
  max_delay = 30s（封顶）
重连成功回调：自动 resubscribeAll(订阅表在内存中保留)
断线处理：WsService 启动 degradeWatchdog（5s 检测一次 → 降级 HTTP 轮询兜底）
```

### 10.5 实际代码中的特殊处理

实际 `IbmcpWsClient.ts` 在 `onMessage` 里做了几个设计稿没提到的特殊处理：

1. **批量 data 消息展开**：`type === 'data_batch'` 时把数组拆成 N 条单点位消息分别 dispatch
2. **device_status 特殊分发**：payload 中 `type === 'device_status'` 时更新全局 `deviceStatus` Map
3. **订阅状态去重**：`subscribe(topic)` 只在首次未订阅时发送 `{"type":"subscribe"}`，已订阅则不再发（但会把订阅者计入计数器）

router.beforeEach((to, from, next) => {
  const auth = useAuthStore()
  
  if (to.path === '/login') { next(); return }
  
  // 未登录 → 跳登录页
  if (!auth.token) { next('/login'); return }

  if (requiredRole && !userRoles.includes(requiredRole)) {
    next('/403'); return
  }
  
  next()

        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;

## 十六、字段命名与类型约定

### 16.1 命名风格差异

⚠️ **当前现状**：实际前端代码（TypeScript/JS 生态惯例）在**所有边界层**都用**驼峰命名**，包括：

- HTTP 请求 query 参数：`GET /api/history?pointId=123&start=...&agg=avg`
- HTTP 响应读取：`resp.data.data.deviceId`（实际用 `data` 还是 `items` 取决于旧后端返回）
- WS 载荷：`payload.deviceId` / `payload.pointId` / `payload.alarmId` / `payload.triggeredAt`

**03 号文档的硬约束**：后端全蛇形（`device_code` / `point_id` / `triggered_at`），前端**必须在边界层做驼峰↔蛇形转换**。

**建议方案（推荐方案 A）**：

| 方案                        | 说明                                                                                                                           | 改动量                                                 |
|-----------------------------|--------------------------------------------------------------------------------------------------------------------------------|--------------------------------------------------------|
| **A：前端对齐后端全蛇形**   | 统一在 `types/api.ts` 的 interface 定义中用蛇形字段名，让 `httpService` 自动 pascalCase→snakeCase（或用 `camel-case-keys` 库） | 小改动，集中改 interface 定义 + httpService 加自动转换 |
| B：后端对齐前端全驼峰       | Python 后端用 Pydantic 的 alias 自动 snake_case↔camelCase                                                                      | 中改动，后端全局 Pydantic 配置                         |
| C：保持现状，接口文档不统一 | 03 号文档说蛇形，实际代码驼峰，靠人脑记                                                                                        | ❌ 不推荐，维护成本高                                  |

> 本文档后续所有示例统一用**03 号文档的蛇形命名**（即方案 A），因为后端已经在 03 号中定义为蛇形。
