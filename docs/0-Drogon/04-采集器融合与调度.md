# 04 - 采集器融合与调度

> 核心改造：`backend/collector` 不再通过 pybind11 暴露给 Python，而是编译为静态库 `libibmcp_collector.a`，直接链接进 Drogon 可执行文件。采集与业务同进程、同线程模型，消除跨语言边界。

### 1.3 新增 `CollectorBridge`（替代 Python ffi 适配层）

由于采集器内部用 `map<string,string>` 承载事件/健康/快照，所有数值字段都是字符串；且协议名在采集器内部归一化为无下划线风格（`modbustcp`/`modbusrtu`/`opcua`），但 DB 与前端契约使用带下划线风格（`modbus_tcp`/`modbus_rtu`/`opc_ua`）。

旧架构中这层规范化由 Python `app/core/collector/ffi.py` 完成。新架构在 `backend` 新增 `CollectorBridge` 封装类，把这些规范化逻辑**下沉到 C++ 一次完成**，业务层直接拿到强类型数据：

```cpp
// include/collector/collector_bridge.h
namespace ibmcp {

struct Sample {
    int64_t seq;
    int64_t point_id;
    int64_t ts_ms;
    double value;
    std::string quality;
    std::string raw_value;
    std::string device_key;
};

struct HealthInfo {
    int threads, revision, device_count, point_count, queue_depth, dropped, uptime_sec;
    int devices_real, devices_degraded;
    std::vector<std::string> protocols;  // 已转为 stub 风格 modbus_tcp
};

class CollectorBridge {
public:
    void init(const nlohmann::json& cfg);
    HealthInfo health();
    std::vector<std::string> protocols();             // stub 风格
    nlohmann::json capabilities();                    // stub 风格 + bool/int
    int applyPlan(const nlohmann::json& plan, int revision);
    std::pair<int64_t, std::vector<Sample>> snapshotSince(int64_t sinceSeq);
    int writePoint(const std::string& deviceKey, int pointId, const std::string& value);
    void setEventCallback(std::function<void(const nlohmann::json&)> cb);  // 已规范化
    void shutdown();
private:
    static std::string toStubProtocol(const std::string& name);  // modbustcp→modbus_tcp
    static nlohmann::json normalizeEvent(const std::map<std::string,std::string>& evt);
};
}
```

必须保留的规范化规则（移植自 `ffi.py`）：

| 规则 | 字段 |
|------|------|
| 字符串 → int | 事件：`revision, device_count, point_count, status, point_id, command_id, ts_ms, finished_at, ts, total_samples, queue_depth, dropped, devices_online, devices_degraded`；快照：`seq, point_id, ts_ms` |
| 字符串 → float | 快照 `value` |
| 字符串 → bool | 事件 `success`（必须按字面量解析，避免 `bool("False")==true` 误判写失败为成功）；caps `compiled, supports_write` |
| 协议名映射 | `modbustcp→modbus_tcp, modbusrtu→modbus_rtu, opcua→opc_ua, sockettcp→socket_tcp, socketudp→socket_udp, mqtt→mqtt, websocket→websocket` |

> 这是迁移的**关键正确性红线**：`write_result.success` 若用 `std::stoi` 或 `bool` 直接转换会把 `"False"` 判为真，导致控制命令状态回写错误。必须按字面量 `"true"/"1"/"yes"` 解析。

## 2. 事件回调链路

### 2.1 红线（与旧架构一致）

采集器事件回调在 **C++ 采集工作线程**上执行，回调内**只能做投递**，绝不做 DB / HTTP / 加锁等待，避免阻塞采集线程。

### 2.2 EventDispatcher（C++ 版）

旧 `asyncio.Queue` + 消费协程 → C++ 用「线程安全队列 + 独立消费线程」：

```cpp
class EventDispatcher {
public:
    EventDispatcher(DbClientPtr db, CollectorBridge& collector, WsHub& hub, CommandWaiter& waiter);
    void start();   // 启动消费线程，注册 collector.setEventCallback(...)
    void stop();    // 置回调为 nullptr，停消费线程
private:
    void onEvent(const nlohmann::json& evt);   // 采集线程：只 push 队列
    void run();                                  // 消费线程：handle
    void handle(const nlohmann::json& evt);

    moodycamel::ConcurrentQueue<nlohmann::json> queue_;  // 无锁队列（或 std::queue + mutex）
    std::thread worker_;
    std::atomic<bool> running_{false};
};
```

实际实现采用 `std::queue + std::mutex + std::condition_variable`（`backend/src/collector/event_dispatcher.cpp:37`），队列硬上限 10000，满时丢弃新事件并记 `LOG_WARN`，避免采集回调线程被慢消费拖死。

### 2.3 事件类型处理（移植自 `event_dispatcher.py`）

| event.type | 处理 |
|------------|------|
| `device_status` | UPSERT `using_devices` + `using_device_runtime`；WS 广播 `device` 主题 |
| `write_result` | UPDATE `control_commands`（按 `ext_command_id`）置 status（2 成功/3 失败）；WS 广播 `control` 主题；`CommandWaiter::resolve` 唤醒等待者 |
| `plan_ack` | UPDATE `runtime_plan_revision` 置 status（1 成功/2 失败）+ `applied_at` |
| `collector_stats` | 仅记 debug 日志 |

时间戳取 `ts_ms // 1000`，无则退 `finished_at`/`ts`，再无则当前时间（`_event_seconds` 逻辑）。

## 3. SamplePump（采样泵 C++ 化）

旧 `asyncio` 200ms 循环 → C++ 独立线程循环。逻辑完整移植：

```cpp
class SamplePump {
public:
    SamplePump(DbClientPtr db, const std::string& copyDsn,
               CollectorBridge& collector, WsHub& hub, int flushIntervalMs = 200);
    void start();
    void stop();
private:
    void run();
    void tick();
    void warmupPointCache();   // 预热 using_points 映射（using_point_id → 行）
    void batchCopyTs(const std::vector<TsRow>& rows);  // libpq COPY，专用连接
    void evaluateAlarms(...);   // ActiveAlarmTracker
    void persistAlarms(...);

    int flushIntervalMs_;
    int64_t seq_{0};
    std::thread worker_;
    std::atomic<bool> running_{false};
    ActiveAlarmTracker alarmTracker_;
    std::unordered_map<std::string, PointMeta> pointCache_;  // using_point_id → meta
    PGconn* copyConn_{nullptr};   // 专用 libpq 连接，仅泵线程使用
};
```

### 3.1 单次 tick 流程（对齐旧 `_tick`）

1. `collector.snapshot_since(seq_)` → `(new_seq, samples)`（采集线程外调用，可能短暂阻塞，但泵在自有线程不影响 HTTP）；
2. 若样本中出现未知 `point_id`，刷新 `pointCache_`（计划变更后新点位）；
3. `prepareTsRows`：映射 `point_id → using_points.id`，按 `(ts, point_id)` 去重，`ts_ms` 为空则用 `now*1000`；
4. `batchCopyTs`：libpq COPY 批量写 `time_series_data`，失败回退批量 INSERT ON CONFLICT DO NOTHING；
5. `evaluateAlarms`：逐样本判定（见 §3.2），生成触发/恢复事件；
6. `persistAlarms`：触发则 INSERT `using_alarms`，恢复则 UPDATE 置 state=3；
7. WS 广播：`alarm` 主题（若有事件）+ `data` 主题（本批样本摘要）。

### 3.2 报警判定（ActiveAlarmTracker，完整移植）

内存态活动报警表，key = `(device_code, point_address)`（`backend/src/collector/sample_pump.cpp:60` 的 `ActiveAlarmTracker`，`static` 单例，每次进程启动时为空）。**注意：当前实现不会从 DB 预热已有的 `state=1` 报警**——重启后，重启前已越限的测点需再次越限才会重新触发、回到正常区间才会产生恢复事件，因此重启瞬间内存态与 DB 中残留的活动报警记录可能短暂不一致。判定规则（与旧 `check_and_decide` 完全一致）：

- `alarm_enabled=false` 或 `quality != "Good"` → 不判定；
- `value > alarm_high || value < alarm_low` → 触发/升级：
  - `level=2` 默认；若越限幅度 `> span*0.5`（`span = alarm_high - alarm_low`）则 `level=3`；
  - 无活动报警或非 state=1 → 新建 `state=1` 记录；
  - 已有活动但 level 变化 → 更新 level/value；
- 回到正常区间且存在活动报警 → 弹出并返回 `state=3` 恢复事件。

### 3.3 性能要点

- 采样泵持有**专用 libpq 连接**做 COPY（不走 Drogon 连接池），避免阻塞池内连接影响 HTTP 查询；
- 泵线程与 Drogon IO 线程完全隔离，DB 慢时仅堆积采集器内部无锁缓冲，不拖垮 API；
- 与旧 `asyncio.to_thread` 相比，省掉 GIL 与 Python 序列化，**吞吐更高、尾延迟更低**。

## 4. CommandWaiter（控制命令同步等待 C++ 化）

旧 `asyncio.Future` → C++ `std::promise`/`std::shared_future`：

```cpp
class CommandWaiter {
public:
    // ControlService 调用：注册一个等待，返回 future
    std::shared_future<nlohmann::json> expect(const std::string& deviceKey, int pointId);
    // EventDispatcher 在 write_result 事件中调用：唤醒等待者
    void resolve(const std::string& key, const nlohmann::json& result);
    size_t pending() const;   // /control/queue-depth
private:
    std::mutex mu_;
    std::unordered_map<std::string, std::promise<nlohmann::json>> pending_;
};
```

`key = deviceKey + ":" + pointId`（移植自 `command_key`）。`wait=true` 的控制接口在 Controller 中：

```cpp
Task<HttpResponsePtr> ControlController::write(const HttpRequestPtr& req) {
    // ... 解析 device_key, point_id, value, wait
    auto fut = waiter_.expect(deviceKey, pointId);  // 先注册等待
    auto extId = collector_.writePoint(deviceKey, pointId, value);  // 发命令
    db_->execSqlCoro("UPDATE control_commands SET ext_command_id=$1 ...", extId, ...);
    if (wait) {
        auto result = co_await std::async(std::launch::async,
            [fut] { return fut.get(); });  // 协程等待 future（超时兜底）
        co_return Result::ok(result);
    }
    co_return Result::ok({{"command_id", commandId}});
}
```

> 实际实现（`backend/src/service/control_service.cpp:172`）：不阻塞等待 future，而是在协程里用 `fut.wait_for(0)` 轮询就绪态 + `co_await drogon::sleepCoro(loop, 0.05)` 让出执行，直到 `deadline`。超时参数由请求体 `timeout` 传入，**默认 3.0s**（`backend/src/controller/control_controller.cpp:30`），`wait=true` 时校验范围 `(0, 30]`（`backend/src/controller/control_controller.cpp:59-60`）；超时到达后主动 `waiter.resolve(...)` 写入超时结果并抛出 `BizError(4102)`，避免请求永久悬挂。`wait` 默认 `false`，即发即忘，立即返回 `command_id`。

## 5. 计划编译与下发（PlanCompiler / CollectorOrchestrator）

### 5.1 PlanCompiler（C++ 重写）

五级配置链（装备配置 → 路线 → 步骤设备 → 设备采集点 → 数据项字典）编译为采集器 `plan` JSON。逻辑从 `backend/app/services/plan_compiler.py` 完整移植，输出格式与采集器 `apply_plan` 期望的 schema 完全一致（采集器端 `plan_parser` 不变，所以编译产物 schema 不变）。

### 5.2 CollectorOrchestrator（C++ 重写）

负责：
- 启动 `bootstrap`：加载所有 `config_status=已发布` 的配置，编译并下发；
- 配置变更（activate / unload / recompile / sync）时重编译；
- **版本幂等**：计算 `plan_hash`，查 `runtime_plan_revision`，hash 未变则跳过下发；
- 写入 `runtime_plan_revision` 记录 revision 与 hash，`status` 由 `plan_ack` 事件回填。

### 5.3 计划 JSON 构建

`apply_plan` 接收的 `plan` 是 `nlohmann::json`，由 `PlanCompiler` 组装。采集器内部 `plan_parser` 解析，**此契约不变**，确保采集器代码零修改。

## 6. 启动与关停顺序

`main.cpp` 中的生命周期（对齐旧 `lifespan`）：

```
启动（`backend/src/main.cpp` + `backend/src/core/app_context.cpp`）：
1. `app().loadConfigFile("config.json")` —— 加载监听/线程/日志/DB 客户端/custom_config
2. `Migrator::migrate()` —— DB schema 迁移（同步、libpq 直连，在监听前完成）
3. 注册全局 Advice / 异常处理器 —— CORS 后置、Post-Routing 鉴权、`BizError` 异常兜底
4. `registerBeginningAdvice` 中执行 `AppContext::init()`：
   a. `CollectorBridge::init(cfg)` —— 启动采集器线程池/时间轮
   b. `EventDispatcher::start()` —— 注册采集事件回调
   c. 构造 `CollectorOrchestrator`
   d. `SamplePump::start()` —— 启动采样泵线程
5. 紧接着（同 beginning advice，异步协程）`CollectorOrchestrator::bootstrap()` —— 下发已发布计划
6. `app().run()` —— 阻塞，监听端口

> `WsHub` 是进程单例（`ws::WsHub::instance()`），在首次被 `EventDispatcher`/`SamplePump` 引用时懒构造，无独立构造步骤。

关停（SIGINT/SIGTERM）：
1. SamplePump::stop()
2. EventDispatcher::stop()      —— detach 回调，停消费线程
3. CollectorBridge::shutdown()  —— 停采集器调度
4. app().quit()                 —— Drogon 退出
```

Drogon 的 `app().run()` 会捕获信号；可在 `run()` 前注册 `app().setSignalHandler` 或直接在信号回调里按上述逆序关停。

## 7. 线程模型汇总

| 组件 | 线程 | 与旧架构对应 |
|------|------|-------------|
| HTTP/WS 收发 | Drogon IO 线程池（`setThreadNum`） | 旧 asyncio 事件循环 |
| DB 查询 | Drogon DbClient 异步回调线程 | 旧 asyncpg |
| COPY 批量写入 | SamplePump 专用线程 + 专用 libpq 连接 | 旧 asyncio + to_thread |
| 采集调度/协议 IO | collector 静态库内部（时间轮 + IO 池） | 同（旧也在 C++ 内） |
| 事件消费 | EventDispatcher 消费线程 | 旧 asyncio.Queue 消费协程 |
| 控制命令等待 | `std::future`，不占线程 | 旧 asyncio.Future |
