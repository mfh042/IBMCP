## 3. 必须保持一致的行为（迁移红线）

以下行为若变更会破坏前端或业务正确性，迁移时**必须逐字核对**：

1. **统一响应包膜**：HTTP 恒 200，`{code, message, data}`，`code=0` 成功，业务错误 code 非 0（见 03 §4）。
2. **鉴权失败**：401/403 也走包膜（HTTP 200，code=401/403），不是裸 HTTP 错误码（旧 `http_exception_handler` 行为）。
3. **`write_result.success` 解析**：采集器传字符串 `"True"`/`"False"`，必须按字面量解析，**禁止** `bool("False")` 式强转（会把失败判为成功）。见 04 §1.3。
4. **协议名风格**：对外（DB/前端/API）一律用下划线风格 `modbus_tcp`/`modbus_rtu`/`opc_ua`/`socket_tcp`/`socket_udp`；采集器内部无下划线风格由 `CollectorBridge` 转换。见 04 §1.3。
5. **事件字段类型**：事件/快照中的数值字段原为字符串，`CollectorBridge` 必须规范化回 int/float（`seq/point_id/ts_ms/value/revision/...`）。
6. **报警判定规则**：level 计算（`span*0.5` 阈值升 3 级）、活动报警内存跟踪、恢复置 state=3，与旧 `ActiveAlarmTracker` 完全一致（见 04 §3.2）。
7. **时序写入去重**：按 `(ts, point_id)` 去重，COPY 失败回退 INSERT ON CONFLICT DO NOTHING（见 04 §3.1）。
8. **计划下发幂等**：`plan_hash` 不变则跳过 `apply_plan`，revision 单调递增（旧 `CollectorOrchestrator` 行为）。
9. **控制命令 wait 超时**：旧有超时兜底，C++ 版必须保留，禁止无限等待（见 04 §4）。
10. **时间戳**：`ts_ms` 来自采集器；事件时间取 `ts_ms//1000`，退 `finished_at`/`ts`，再退当前（旧 `_event_seconds`）。
11. **CORS**：开发期放开白名单，与旧 `CORS_ORIGINS` 一致。
12. **WS 路径双兼容**：`/ws/push`（新）与 `/api/v1/ws/collect`（旧）都可用，前端无需改。

## 6. 风险与缓解

| 风险 | 影响 | 缓解 |
|------|------|------|
| `success` 字符串误判 | 控制命令状态错误（失败显示成功） | `CollectorBridge` 单测覆盖 `"False"`→false；红线 3 |
| 协议名未转换 | 前端/DB 数据不一致 | 单测覆盖 `modbustcp→modbus_tcp` 全量映射；红线 4 |
| COPY 阻塞 Drogon 池 | API 卡顿 | SamplePump 用专用 libpq 连接，隔离池（04 §3.3） |
| `wait=true` 无限等待 | 请求悬挂、连接耗尽 | future 加超时（默认 3s，`wait=true` 时可配，上限 30s），超时抛 `BizError(4102)` 返回 code 非 0（04 §4） |
| C++20 协程与 future 兼容 | 编译/运行错误 | 用 `fut.wait_for(0)` 轮询就绪态 + `co_await drogon::sleepCoro` 让出执行（`backend/src/service/control_service.cpp:172`），不阻塞 IO 线程；已在欧拉上编译验证 |
| Drogon 版本与 libpq 不匹配 | 编译失败 | 在欧拉上源码编译 Drogon（05 §3.4），锁定 v1.9.x |
| 存量数据迁移 | 首次部署需建基线 | SQL 脚本用 `IF NOT EXISTS`，幂等；首次写入 `schema_migrations` 基线版本 |
| 前端路径依赖 | 前端可能硬编码某些响应细节 | 迁移期保留双路径与包膜兼容；用前端构建产物做端到端回归 |
| Windows 开发体验 | 旧需 stub，现需本地装 Drogon | 纯 C++ 后 Windows 可用 vcpkg 装 Drogon 直接编译调试；仍以欧拉为目标环境 |

## 7. 回滚方案

迁移采用「新旧并行、逐步切流」时的回滚：
- 新旧后端监听不同端口（新 8000，旧临时 8001），nginx `proxy_pass` 一行切换；
- 数据库 schema 向后兼容（迁移脚本均 `IF NOT EXISTS`/增量列，不删列），新旧可同库运行；
- 若新系统故障，nginx 切回旧端口，`systemctl restart ibmcp-api`（旧 unit）即可恢复；
- 稳定运行 1~2 周后再删除旧 `backend/` 与旧 systemd unit。
